## 2. 측정으로 확정한 사실 — 전제 세 개를 고쳐야 한다

**(a) Lua 5.4가 아니라 5.2.4다.** `femto8/src/lua/lua.h:19-22` (`LUA_VERSION_NUM 502`,
`LUA_VERSION_RELEASE "4"`). 바이트코드 포맷은 5.2의 `luaU_dump`/`luaU_undump`이고,
`lundump.c:190-201`이 헤더에서 **`sizeof(int)`·`sizeof(size_t)`·`sizeof(Instruction)`·
`sizeof(lua_Number)`** 네 값을 비교한다(엔디안은 헤더에 없고 네이티브 바이트 순서를 그대로 쓴다).

**(b) 숫자는 이미 fix32_t다 — "더 가벼운 값 표현"은 이미 되어 있다.**
`luaconf.h:552-588`이 기본 `double` 정의를 `#undef`하고 `LUA_NUMBER fix32_t`로 다시 정의한다
(`luai_numadd`…`luai_numrotl`까지 전부 `fix32_*`). wasm32에서 실측한 크기:

| TValue | Node | TString | Proto | Instruction | int | size_t | lua_Number |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 8 | 20 | 16 | 80 | 4 | 4 | 4 | 4 |

→ "값 표현을 4 B로 줄이는 더 가벼운 VM" 안은 **이미 적용된 상태**다. 남은 절감 여지는 없다.

**(c) 컴파일 비용은 크지만, 피크를 정하는 건 카트에 따라 다르다.**
wasm32에서 같은 소스를 `luaL_loadbuffer` + `lua_dump`로 재어 본 값(요청 바이트, Lua 쪽만):

| 카트 | 소스 | 바이트코드 | bc/소스 | 컴파일 피크 | 바이트코드 로드 피크 | 컴파일 | undump |
|---|---:|---:|---:|---:|---:|---:|---:|
| baba | 45,053 | 71,619 | 1.59 | 152,517 | 79,760 | 12.5 ms | 0.6 ms |
| bunny | 49,966 | 87,071 | 1.74 | 190,566 | 100,877 | 5.1 ms | 0.6 ms |
| fighter | 39,786 | 76,324 | 1.92 | 160,749 | 90,925 | 3.7 ms | 0.7 ms |
| flipside | 8,268 | 17,697 | 2.14 | 41,946 | 23,801 | 1.1 ms | 0.1 ms |
| loop-4 | 12,089 | 30,057 | 2.49 | 62,775 | 38,356 | 1.7 ms | 0.7 ms |
| terra | 40,944 | 89,766 | 2.19 | 163,532 | 105,461 | 10.5 ms | 0.3 ms |

(측정 방법: `femto8/src/lua/*.c`를 **wasm32로 그대로** 컴파일해 `luaL_loadbuffer`→`lua_dump`,
할당자는 요청 바이트를 세는 래퍼. 소스는 `pico8_code_section_decompress`로 카트에서 뽑았다.
스크래치: `build/luabc/{compile.c,measure.mjs,dump_script.c}`.)

**(d) terra의 172 ms/프레임은 GC 탓이 아니다.** 아레나를 1 MiB로 키워 거부를 0으로 만든 뒤
다시 재면 **180 ms/프레임**이다(거부 119,027 → 0, 프레임 시간은 그대로). 즉 terra는
인터프리터 자체가 느린 카트다. 반대로 baba는 0.65 ms/프레임 — 이미 충분히 빠르다.

**(e) bunny는 "로드"에서 죽는다.** peak@1 == peak@300 == 411,960이고 status는 로드 실패다.
1 MiB 아레나에서는 **로드에 성공해 7.88 ms/프레임으로 돈다**. 즉 bunny의 병목은 런타임이 아니라
컴파일 순간이다.

## 3. 설계안 3개

공통 전제: 페이지가 업로드 시점에 **femto8의 Lua를 wasm32로 컴파일한 것**으로 바이트코드를 만든다
(같은 소스·같은 `luaconf`·같은 파서 패치 → 기기가 만들 바이트코드와 동일). ABI는 (a)의 네 크기 +
리틀엔디안: wasm32와 pi32v2 모두 4/4/4/4다.

### 안 A — 비압축 바이트코드, 슬롯 2개를 한 카트에, 플래시에서 직접 undump

`hh_cart_data()`는 이미 **XIP 포인터**를 돌려준다(`src/picovave.c:549-553`,
`FL_XIP(FL_DATA_LO+off)`). 그래서 슬롯의 바이트코드를 `lua_load(L, reader, …)`로 **RAM 복사 없이**
읽을 수 있다. 소스 버퍼도, 압축해제 버퍼도, 컴파일러도 로드 경로에서 사라진다.

| | baba | 64 KB 카트 |
|---|---|---|
| 로드 시 Lua 추가분 | 152,517 + 45,053 = **197,570** → **79,760** (−118 KB, −60%) | 223,000~262,000 + 65,535 = **288~328 KB(현재는 로드 불가)** → **116~167 KB** |
| peak@1 (엔진 110 KB + 위 + 첫 프레임 69 KB) | 376 KB → **~259 KB** | — |
| peak@300 (런타임) | **412 KB (불변)** | 데이터가 많으면 여전히 실패 |
| 프레임 시간 | **0%** (같은 VM, 같은 opcode) | 0% |
| 부팅 | 12.5 ms → 0.6 ms (wasm, 20×) | 같음 |
| 슬롯 | 71,619 ≤ **105,660** ✓ | 104~143 KB → **경계/초과** ✗ |

슬롯 예산: 두 슬롯 통합 payload 122,816 − 매직 4 − ROM 17,152 = **105,660 B**.
terra 89,766까지 들어가고, 64 KB 카트는 안 들어갈 수 있다(그때는 소스 카트로 폴백 = 오늘과 동일).

- 리스크: **롤백 슬롯 상실**(업로드 중 전원이 끊기면 카트가 없다 — 내장 카트는 산다),
  바이트코드 ABI 잠금(엔진의 Lua/파서를 고치면 페이지 컴파일러도 같이 배포해야 한다).
- 64 KB 카트가 안 들어가는 경우의 보완: 덤프에서 디버그 정보(lineinfo/locvars)를 떼면 30% 안팎 줄어든다
  (5.2 `lua_dump`에는 strip 인자가 없다 — 페이지 쪽 덤프만 패치).

### 안 B — 압축 바이트코드 + 기기 inflate, 슬롯 1개 유지

바이트코드는 deflate로 **2.8~3.3×** 줄어든다(측정: baba 71,619→23,431, terra 89,766→31,689).

| | baba | 64 KB 카트 |
|---|---|---|
| 슬롯 | 23,431 ≤ **44,220** ✓ | 34~51 KB → 경계 |
| 로드 메모리 | A와 같거나 +32 KB(윈도우) | 같음 |
| 프레임 | 0% | 0% |
| 비용 | inflate ~4 KB XIP 신규 + 32 KB 윈도우 | — |

- 장점: **롤백 슬롯 유지**, 업로드 중단 내성 유지.
- 단점: 플래시 직접 undump가 불가능해져 스트리밍 inflate 리더를 써야 하고, 코드가 늘어난다.
- 참고: 트리에 PXA **압축기**는 없다(해제기만 있다). 페이지에서 PXA를 만들려면 JS 포팅이 필요하고
  바이너리 데이터에서의 비율은 미측정 — deflate(`CompressionStream`)가 확실하다.

### 안 C — AOT (Lua → pi32v2 네이티브)

| 항목 | 값/판정 |
|---|---|
| 프레임 시간 | 유일한 레버. 다만 terra 180 ms → 33 ms는 **5.5×**가 필요하고, 인터프리터 대비 AOT 이득은 통상 2~3×다 → **terra는 여전히 불가** |
| 코드 크기 | 바이트코드의 절반이 코드라면 ~36 KB → 9,000 insn × 8~12 B = **카트당 72~108 KB** |
| 코드가 살 곳 | 카트 저장소 `0x9D000`은 `FM1_XIP`로 CPU **`0x02099000`**에 매핑된다(`fm1_xip.h:11`). 데이터 읽기는 이미 그렇게 한다(`picovave.c:549-553`). 막는 것은 ① PC 가드 창이 `[0x02000120,_etext]`라 그 주소에서 fetch하면 DBG bit 12(`fm1_guard.h:17,77-78`) — 우리 코드이므로 넓히면 됨, ② SFC/XIP 캐시가 그 영역의 **명령 fetch**를 서비스하는지는 **미검증**(실기 1회로 확인 가능) |
| 그 밖 | 고정 주소 링크 + 펌웨어 함수용 고정 점프 테이블(주소가 빌드마다 바뀐다), 72~108 KB > 슬롯 61,440 → 두 슬롯 통합/압축 |
| 결론 | 별도 프로젝트. 지금 하면 안 된다 |

## 4. 추천 — 안 A, 2단계

**왜 A인가.** 브리프의 "중복 계층"은 정확히 두 개다: 소스 압축해제(45 KB 버퍼)와 컴파일(152 KB 피크).
A는 둘 다 로드 경로에서 지우고, 그 대가로 잃는 것은 롤백 슬롯 하나뿐이다. 반면 **프레임 시간은
어떤 사전 컴파일로도 줄지 않는다**(같은 VM이 같은 opcode를 실행한다 — 측정 (d)).
속도가 목표라면 A는 부팅 시간만 줄인다(12.5→0.6 ms, wasm 기준 20×). 이 점을 오해하면 안 된다.

### Stage 0 — 빨간 게이트부터 (4줄)
`host/alloc_test.c:32`, `sim/device_alloc.c:29`, `sim/sim_test.mjs`, `web/sim/index.html`의
414,184 → 414,952. 이걸 먼저 해야 이후 측정이 실기와 같은 수를 말한다.

## 5. 이 설계가 **해결하지 않는** 것 (미리 못 박기)

- **terra의 프레임 시간**: 180 ms/frame은 인터프리터 비용이다(측정 (d)). A로는 1 ms도 안 줄어든다.
- **데이터가 무거운 카트**: 런타임 피크는 그대로다. 64 KB 카트도 코드가 무거우면 살고 데이터가 무거우면 죽는다.
- **기기 실측 프레임/부팅**: 위 시간은 전부 wasm이다. 비율(컴파일:undump = 20:1)은 유효하지만
  절대값은 기기에서 다시 재야 한다.
- **64 KB 실카트 없음**: §3의 64 KB 행은 소스 바이트당 비율(3.4~4.0 컴파일, 1.6~2.2 바이트코드)의
  **선형 외삽**이다. 실제 64 KB 카트로 확인하기 전에는 확정이 아니다.

## 6. "femto8를 거치지 않고 pi32v2 네이티브로" — 검토 (2026-10-19 추가)

**먼저 사실 하나: femto8은 이미 pi32v2 네이티브다.** `p8_emu.c`·`p8_lua.c`는 clang
`-target pi32v2`로 컴파일되어 XIP(`0x02000120`)에서 실행된다(`tools/build_picovave.py:55`).
카트와 CPU 사이에 있는 인터프리터는 **Lua 하나뿐**이고, femto8은 그 Lua를 호출하는 C 코드다.
따라서 "femto8를 거치지 않는다"가 없앨 수 있는 것은 **엔진의 고정 프레임 비용**뿐이다. 그 크기를 쟀다.

### 6.1 프레임 비용 분해 (합성 카트, 기기 allocator, wasm)

| 워크로드 | ms/frame | 유도 |
|---|---:|---|
| 빈 카트 (`_update`/`_draw`만) | **0.052** | femto8 고정 비용(렌더 128×128 + 표시 + 오디오) |
| 1.97M 단순 덧셈 | 18.18 | **9.2 ns / 반복**(VM 명령 몇 개) |
| 1.97M 테이블 읽기 | 45.67 | **23 ns / 반복** |
| 20,000 pset | 1.305 | **65 ns / 호출** |
| 2,000 spr | 0.384 | **192 ns / 호출** |
| 300 print | 0.268 | 0.9 µs / 호출 |
| baba (실카트) | 0.65 | — |
| terra (실카트) | 172.3 | — |

(합성 카트는 `build/luabc/synth.mjs`. 주의: fix32 상한이 32767.999라 루프 한계를 그 위로 두면
루프가 **한 번도 돌지 않는다** — 처음에 200k/2M로 쟀을 때 0.04 ms가 나온 이유다. 중첩 루프로 고쳤다.)

**결론 1 — femto8 자체를 없애서 얻는 상한은 0.052 ms/프레임이다.**
baba의 **8%**, terra의 **0.03%**다. terra의 172 ms는 Lua VM이 카트 코드를 실행하는 시간이고,
femto8은 그 시간에 관여하지 않는다.

### 6.2 메모리 분해 (baba, 근사)

| 항목 | 크기 | 네이티브 재작성으로 제거 가능? |
|---|---:|---|
| `m_memory` (PICO-8 64 KiB 주소공간, `p8_emu.h:112`) | 65,536 | **불가** — gfx/map/sfx/화면이 사는 곳. 어떤 PICO-8 런타임이든 필요 |
| `m_overlay` (I/O 아이콘) | 8,192 | 가능 |
| Lua 상태 + 라이브러리 | ~30,000 | AOT면 가능 |
| Proto + 문자열 (baba) | ~79,800 | AOT면 가능 |
| 카트의 런타임 데이터·스택·GC 여유 | ~230,000 | **불가** — 게임 데이터 그 자체 |

즉 네이티브로 갈 때 baba의 412 KB는 **~300 KB**까지 내려간다(Proto+L 제거). 64 KB 카트의
데이터가 무거우면 그 데이터는 그대로 남는다 — 메모리 문제의 본질은 코드 계층이 아니다.

### 6.3 그래서 "네이티브"의 실체 = Lua AOT + API 레이어 재작성

- **코드 크기**: 카트당 72~108 KB(§3 안 C). 카트 저장소는 `FM1_XIP(0x9D000)` = CPU
  **`0x02099000`**에 매핑되어 있고(`fm1_xip.h:11`), 데이터 읽기는 이미 그 포인터로 한다
  (`src/picovave.c:549-553`). 즉 "실행 불가"가 아니라 **아직 아무도 fetch를 시도하지 않은 것**이다.
  막는 것은 PC 가드 창(`[0x02000120,_etext]`, `fm1_guard.h:17,77-78`) — 우리 코드라 넓히면 되고 —
  그리고 SFC/XIP 캐시가 그 영역의 명령 fetch를 서비스하는지에 대한 **미검증** 하나다.
  실기 1회(저장소에 작은 함수를 심고 호출)로 답이 나온다.
- **그 밖의 진짜 비용**: 고정 주소 링크 + 펌웨어 함수용 고정 점프 테이블(함수 주소가 빌드마다 바뀐다),
  카트당 72~108 KB > 슬롯 61,440 B(두 슬롯 통합 또는 압축), 그리고 Lua→pi32v2 AOT 컴파일러 자체.
- **작업량**: `p8_lua.c` 2,809줄 + `p8_emu.c` 1,236줄 + 대체할 Lua 코어 16,643줄.
- **terra**: 172 ms → AOT 2~3×로 60~90 ms 추정. 33 ms(30 fps)에는 못 간다. 여전히 못 쓴다.
- **네이티브가 실제로 이기는 곳**: 부팅(컴파일 제거), API 호출 오버헤드(65 ns → 직접 호출),
  그리고 데이터가 가벼운 카트의 프레임. baba 같은 카트에는 이미 의미가 없다(0.65 ms).

### 6.4 "손으로 C로 옮긴다" vs "Lua를 pi32v2 바이너리로 만들어 매번 플래싱" — 다른 것

| | 손 포팅 | 자동 AOT (안 C) |
|---|---|---|
| 누가 변환 | **사람**이 게임 로직을 C로 다시 씀 | **컴파일러**가 Lua를 기계어로 |
| 카트 호환 | 없음 — 그 게임 전용 빌드 | 유지 — 아무 카트나 |
| 코드가 사는 곳 | 펌웨어 이미지에 링크 | 카트 저장소(가능하면) 또는 펌웨어 |
| 배포 | **게임당 1회 빌드·플래시**, OTA하면 사라짐 | 업로드로 끝날 수 있음(아래 조건) |
| 속도 | 10~100× (Lua 객체 모델 자체를 버림) | 2~3× (VM 디스패치만 제거) |
| 메모리 | 데이터 구조를 C로 재설계 → 가장 큰 절감 | Proto/L 상태만 제거 (~110 KB) |

"매번 플래싱"이 되는 경우는 두 가지다: **(a)** 손 포팅(펌웨어에 링크하므로), **(b)** 자동 AOT인데
저장소에서 명령 fetch가 안 되는 것으로 판명될 때. 반대로 fetch가 되면 AOT 카트는 **업로드만으로**
동작하고 OTA에도 살아남는다(저장소는 업데이트가 건드리지 않는다 — `fm1_flash_map.h:27`).
즉 "플래싱"은 AOT의 본질이 아니라 **아직 검증되지 않은 하드웨어 가정의 결과**다.

**결론 2 — 지금 할 이유가 없다.** 같은 "중복 계층 제거"를 안 A는 4~5개 파일로 달성하고,
네이티브 재작성은 실행 모델·툴체인·API 전부를 다시 쓰는 별도 프로젝트다. 얻는 것은
프레임의 8%(baba)이고, 정작 문제인 terra는 어느 쪽으로도 살아나지 않는다.
예외는 **특정 카트를 손으로 C로 옮기는 것**인데, 그것은 PICO-8 런타임이 아니라 게임 포팅이다
(10~100× 가능하지만 카트를 더 이상 받을 수 없고, 게임마다 펌웨어를 다시 플래시해야 한다).
